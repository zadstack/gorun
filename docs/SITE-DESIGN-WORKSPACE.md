# Site design workspace

Website → Design contains one **Site design** entry. The saved site summary and two page tabs are shared by the existing Build site and Visual identity screens. The summary reads stored site settings (with the same default fallback for absent/invalid shared identity); edits in either form do not appear there until saved/applied.

`/admin/site-design` chooses Build site only when the signed-in user has all five existing permissions: `settings.manage`, `content.create`, `content.edit`, `content.publish`, and `menus.manage`. Settings-only users land on Visual identity and receive no Build tab. The existing `/admin/site-builder`, draft review query URLs and `/admin/appearance/identity` links continue to work. Permission checks on the original GET/POST routes are unchanged.

Build site retains its three-step design/profile/draft workflow, pending-page previews, expected-version activation check and explicit activation action. Creating draft pages does not change the current public homepage or theme. Identity (`/admin/appearance/identity`, owned by the theme module) edits the site identity contract described in [THEMES.md](THEMES.md#site-identity): logos, name, tagline, colours with a contrast check, Arabic and Latin fonts, scheme, corners, spacing, header link and custom CSS. Edits are kept as a per-theme draft that the live preview iframe renders (desktop/mobile, home/post, Arabic/English); **Apply** writes the live settings and records a revision, **Revert** restores an earlier one, and neither touches content. The builder's own `builder.identity` remains a fallback layer and can be imported into the draft. The saved summary shows the effective colours (site identity › builder identity › theme). Switching tabs never submits or activates either form. With JavaScript, edited forms ask before discarding changes on a workspace-tab switch and use the browser's standard unload warning for other navigation.

Validation errors stay on the form's selected workspace page and receive focus when JavaScript is available. A failed POST does not repeat a prior `?saved=1` success notice. Without JavaScript, both links and native forms work, all starter steps remain visible, and a narrowly scoped fallback prevents the legacy sticky admin sidebar from covering this workspace's forms.

The existing `site-builder` navigation ID is retained. The duplicate `builder.identity` registry entry is removed; an old identity deep link remains valid. The dependent Quick access navigation increment projects old `builder.identity` pins to the authorized canonical `site-builder` entry and deduplicates the pair without changing stored preferences. This alias must be included with the workspace when releasing the combined navigation changes. No customer identity is reset and no data migration is required.
